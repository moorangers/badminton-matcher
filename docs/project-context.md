# Project Context

## นี่คือโปรเจกต์อะไร

**Badminton Matcher** — เว็บแอปช่วยจัดคู่ผู้เล่นแบดมินตันหน้างานแบบ Singles (1v1) หรือ Doubles (2v2) ให้กับกลุ่ม/ชมรมตีแบดที่เล่นแบบ walk-in ไม่ใช่ทัวร์นาเมนต์ทางการ เป้าหมายคือ "จัดคู่ให้แฟร์ ไม่ต้องมีคนนั่งจดสถิติเอง"

Tagline ในแอป: *Fair · Fast · Fun*

## แก้ปัญหาอะไร

เวลาคนมาเล่นแบดกันเป็นกลุ่มใหญ่ (10-30+ คน) กับคอร์ดจำนวนจำกัด (1-3 คอร์ด) จะมีปัญหาซ้ำ ๆ:

- จำไม่ได้ว่าใครเล่นไปกี่รอบแล้ว ใครควรได้เล่นก่อน
- คนบางคนได้เล่นบ่อยกว่าคนอื่นเพราะจัดคู่มือ/สุ่มแบบไม่มีระบบ
- ต้องมีคนคอยจดชื่อคู่ถัดไปตลอดเวลา

แอปนี้ automate เรื่องนี้ให้: เพิ่มชื่อผู้เล่น → กดจับคู่ → ระบบสุ่มคู่ตามรอบ (ให้ความสำคัญคนที่เล่นน้อยกว่าก่อน) → จบแมตช์แล้วเลื่อนคิวถัดไปให้อัตโนมัติ

## ผู้ใช้เป้าหมาย

กลุ่ม/ชมรมตีแบดแบบสังสรรค์ (ไม่ใช่ทัวร์นาเมนต์แข่งขันจริงจัง) — ตอนนี้เป็นภาษาไทยเป็นหลัก (UI, toast message ทั้งหมดเป็นภาษาไทย) บ่งชี้ว่า target user คือกลุ่มคนไทย

## สถานะปัจจุบัน (ณ 2026-09-06, v0.5.0)

- **ย้ายจาก client-only + localStorage มาเป็น MongoDB-backed แล้ว**: Next.js API Routes + mongoose + PIN-per-session auth ดูรายละเอียด endpoint ทั้งหมดที่ [database-design.md](./database-design.md) — [project-context.md](./project-context.md) ฉบับก่อนหน้าเคยอธิบายว่าเป็น client-only ล้วน จุดนั้น**ล้าสมัยแล้ว**
- session id + PIN คือหน่วยของ "ห้อง" ตอนนี้ — เปิดจากเครื่องไหนก็เข้าห้องเดียวกันได้ถ้ารู้ PIN (แต่ยังไม่มี realtime sync ข้ามอุปกรณ์พร้อมกัน แต่ละเครื่องต้อง refresh เองถึงจะเห็นข้อมูลล่าสุด)
- ใช้งานจริงยังเหมาะกับ 1 คนถือมือถือ/แท็บเล็ตเครื่องเดียวคุมทั้งกลุ่มเหมือนเดิม (เช่น แอดมินชมรมยืนหน้าคอร์ดคอยกดจับคู่/จบแมตช์) — multi-device พร้อมกันแบบ real-time ยังไม่ใช่ use case ที่รองรับ (รอ Phase 4 realtime layer)
- Business logic การจับคู่ (algorithm) ยังอยู่ฝั่ง client เหมือนเดิมใน [src/features/home/home-page.tsx](../src/features/home/home-page.tsx) — เปลี่ยนแค่แหล่งข้อมูล/ปลายทางจาก localStorage เป็น API เท่านั้น ไม่ได้ย้าย algorithm ไปรันฝั่ง server
