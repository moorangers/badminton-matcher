# Matching Algorithm

หัวใจของแอปคือการสุ่มจับคู่ให้แฟร์ — เอกสารนี้อธิบาย logic เดิม ปัญหาที่พบ และดีไซน์ที่แก้ไปแล้ว (Phase 1 ใน [roadmap.md](./roadmap.md))

> **อัปเดต 2026-09-06:** ส่วน "ดีไซน์ที่เสนอ" ด้านล่าง implement แล้วใน `src/features/home/home-page.tsx` (queuedAt tie-break, partner-history penalty, ปุ่มปิด/รวมคอร์ด) ส่วน "Logic ปัจจุบัน" ในหัวข้อถัดไปอธิบายพฤติกรรม**ก่อน**การแก้ไข เก็บไว้เพื่ออธิบายที่มาของปัญหา

## Logic เดิม (ก่อนแก้ไข)

โค้ดหลักอยู่ใน [home-page.tsx](../src/features/home/home-page.tsx):

1. **`rankCandidates`** (บรรทัด 317-345): จัดกลุ่มผู้เล่นตาม `player.matches` (จำนวนแมตช์สะสมที่เล่นจบไปแล้ว) จากน้อยไปมาก ภายในแต่ละกลุ่มที่ `matches` เท่ากัน แบ่งเป็น 2 กลุ่มย่อย: คนที่ไม่อยู่ใน `recentlyPlayedIds` (ขึ้นก่อน) กับคนที่อยู่ (ขึ้นหลัง) แล้ว shuffle สุ่ม (Fisher-Yates) แยกกันในแต่ละกลุ่มย่อย
2. **`buildMatchesFromPlayers`** (บรรทัด 347-384): ใช้ pool ที่ rank แล้ว ตัดเรียงเข้าคอร์ดทีละคอร์ดตามจำนวนคนที่ต้องใช้ต่อแมตช์ (2 สำหรับ singles, 4 สำหรับ doubles) แบ่งครึ่งแรกเป็น teamA ครึ่งหลังเป็น teamB
3. **`recentlyPlayedIds`** ที่ส่งเข้าไปแต่ละครั้ง คือ "คนที่กำลังเล่นอยู่ในคอร์ดอื่นตอนนี้" (`getActivePlayerIds`) — **ไม่ใช่** "คนที่เพิ่งเล่นจบรอบที่แล้ว" ผลคือ: กรณีมี **1 คอร์ดเดียว** ตัวแปรนี้จะว่างเปล่าเสมอตอน generate คิวถัดไป เพราะไม่มีคอร์ดอื่นที่ "กำลังเล่นอยู่" ให้เทียบ

## ปัญหาที่พบ (ที่มาของ user complaint)

### ปัญหา 1: "1 คอร์ด 8 คน เล่นคู่ แทบไม่เปลี่ยนคู่เลย"

สาเหตุ: การจัดสรรว่า "4 คนไหนได้ลงคอร์ด" ทำงานถูกต้อง (สลับ 2 กลุ่ม 4 คนตาม `matches` count) แต่ **ไม่มีการ track ว่าใครเคยจับคู่เป็นทีมเดียวกับใครมาแล้ว** การแบ่ง teamA/teamB ภายในกลุ่ม 4 คนที่ลงคอร์ดรอบนั้น เป็นแค่ผล side-effect ของการ shuffle สุ่มทั้ง pool แล้วตัดครึ่ง ไม่ได้ตั้งใจกระจาย partner — ทำให้ 2 คนมีโอกาสสุ่มมาจับคู่กันซ้ำได้บ่อยกว่าที่ควรโดยบังเอิญ (มีแค่ 3 combination ของการแบ่งทีมใน 4 คน ทำให้ยิ่งสังเกตเห็นการซ้ำง่าย)

### ปัญหา 2: "มาคอร์สไม่พร้อมกัน อยากแฟร์กับคนมาก่อน"

สาเหตุ: ระบบไม่มีแนวคิดเรื่อง "เวลาที่มาถึง/เข้าคิว" เลย — `Player` มีแค่ `matches` count เป็นตัวจัดลำดับ ถ้าผู้เล่น 2 คนมี `matches` เท่ากัน (เช่น ทั้งคู่ยังไม่เคยเล่นเลย = 0) คนที่มาถึงก่อนกับคนที่เพิ่งมาถึงใหม่จะถูกปฏิบัติเท่ากันหมด แล้วสุ่มล้วน ๆ ว่าใครได้ลงก่อน

## ดีไซน์ที่ implement แล้ว (Phase 1)

โค้ดจริง: `rankCandidates`, `assignTeams`, `incrementPartnerHistory`, `closeCourtNow` ใน [home-page.tsx](../src/features/home/home-page.tsx)

### แก้ปัญหา 2 ก่อน — เพิ่ม wait-time เป็น tie-breaker

เพิ่ม field `queuedAt` (เวลาที่เข้าคิว/มาถึง) ต่อผู้เล่น ปรับ `rankCandidates` ให้ sort ลำดับเป็น:

1. `matches` count (น้อยไปมาก) — เหมือนเดิม เป็นหลักสำคัญที่สุด
2. **`queuedAt`** (เก่าไปใหม่ — มาก่อนได้ก่อน) — ใหม่ แทนที่การแยก "rested vs recently played" แบบเดิมบางส่วน
3. สุ่ม (เป็น tie-breaker สุดท้ายจริง ๆ เมื่อ 1 และ 2 เท่ากันเป๊ะ)

หมายเหตุ: field นี้ต้อง reset เมื่อไหร่ (ทุกครั้งที่จบแมตช์? หรือคงเวลาแรกที่เข้าคิวไว้ตลอด session?) เป็นจุดที่ต้องตัดสินใจตอน implement จริง — น่าจะหมายถึง "เวลาที่กลับเข้าสถานะพักล่าสุด" ไม่ใช่เวลาที่เข้าระบบครั้งแรก

### แก้ปัญหา 1 — partner-history penalty

เพิ่มการนับว่าผู้เล่น 2 คนเคยอยู่ทีมเดียวกันมาแล้วกี่ครั้ง (`partnerHistory`, ดู [database-design.md](./database-design.md)) ตอนจัดทีมภายในกลุ่มคนที่ลงคอร์ดรอบนั้น (ไม่ใช่ตอนสุ่มว่าใครลงคอร์ด) ให้เปลี่ยนจาก "shuffle แล้วตัดครึ่ง" เป็น:

1. สุ่มลำดับผู้เล่นในกลุ่มที่จะลงคอร์ด (เหมือนเดิม)
2. ลองทุก partnership combination ที่เป็นไปได้ในกลุ่มนั้น (4 คน = 3 combos, มากกว่านั้นค่อยคิด heuristic เพราะ combination โตเร็ว)
3. เลือก combination ที่ผลรวม `timesPlayedTogether` ของคู่ที่จะจับกันน้อยที่สุด (ถ้าเสมอกันหลาย combo ค่อยสุ่มเลือก 1 จากในนั้น)

หมายเหตุ: สำหรับ 4 คน (doubles) การลองทุก combination ทำได้ง่ายเพราะมีแค่ 3 แบบ ถ้าในอนาคตมีโหมดที่จัดทีมมากกว่า 4 คนต่อแมตช์พร้อมกันต้องคิด algorithm ที่ scale ได้กว่านี้ (ตอนนี้ยังไม่มี requirement แบบนั้น)

### เกี่ยวกับ Court Merge (ADR-004)

ไม่ใช่ส่วนของ ranking algorithm แต่กระทบ `buildMatchesFromPlayers` ตรงพารามิเตอร์ `plan.courtIds` — เมื่อคอร์ดถูก "ปิด/รวม" ระหว่างเล่น ต้อง:

1. บังคับจบ (`status: 'done'`) แมตช์ที่กำลังเล่นอยู่ในคอร์ดที่ถูกปิดทันที (ต่างจากพฤติกรรมเดิมที่รอให้กดจบเองแมตช์นั้นก่อนถึงจะเลิกเติมคิวคอร์ดนั้น)
2. เอาผู้เล่นจากคอร์ดนั้นกลับเข้า pool ทันที (พร้อม `queuedAt` reset ใหม่ตามเวลาที่ถูกรวม เพื่อไม่ให้เสียเปรียบ fairness)
3. `plan.courtIds` เอาคอร์ดนั้นออกถาวรสำหรับ session/booking period นั้น

## สถานะปัจจุบัน (implemented, client-side/localStorage — ยังไม่ใช่ MongoDB)

- `queuedAt` reset เป็นเวลาปัจจุบันเมื่อ: ผู้เล่นถูกเพิ่มเข้าระบบครั้งแรก, จบแมตช์ (ทั้งทางปกติและถูกปิดคอร์ดแบบ `wasPlaying`), ถูกเปลี่ยนตัวออก (substitute), หรือกด "รีเซ็ตทั้งหมด"
- `partnerHistory` เก็บใน localStorage คีย์ `bm_partnerHistory` (`Record<pairKey, count>`) — ยัง**ไม่แยก scope ต่อ session** เพราะทั้งแอปยังนับเป็น 1 session เดียวอยู่ (ตรงตามข้อจำกัดที่บันทึกไว้ใน [project-context.md](./project-context.md)) จะต้องคิดเรื่อง scope ใหม่ตอนย้ายไป MongoDB จริงใน Phase 0
- `closeCourtNow` (ปุ่ม "ปิดคอร์ด") ตัดคอร์ดออกจาก `activeCourtIds`/`nextPlan` ถาวรสำหรับรอบนั้น, บังคับจบแมตช์ที่กำลังเล่นทันที (นับสถิติ/partner-history เฉพาะกรณี status เดิมเป็น `playing`), แล้ว regenerate คิวคอร์ดที่เหลือใหม่ — เป็น manual trigger เท่านั้น ยังไม่มี auto-timer ตามเวลาจองจริง (รอ Phase 0 มี `courtBookings.endTime`)
- undo stack (`pushUndo`/`undoLast`) ครอบคลุม `partnerHistory` แล้ว เพื่อไม่ให้ state ไม่ตรงกันหลังกด "ย้อนกลับคอร์ดนี้"

## สิ่งที่ยังไม่ตัดสินใจ

- ถ้า partner-history ควร scope แค่ใน 1 session หรือคงข้ามหลาย session ถ้าเป็นกลุ่มคนกลุ่มเดิมมาเล่นทุกอาทิตย์ (ส่งผลกับ schema `partnerHistory.sessionId` ว่าควร nullable/global หรือไม่ — ดู [database-design.md](./database-design.md))
