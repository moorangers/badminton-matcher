# Matching Algorithm

หัวใจของแอปคือการสุ่มจับคู่ให้แฟร์ — เอกสารนี้อธิบาย logic ปัจจุบัน (implement จริงแล้ว, MongoDB-backed) ที่มาของดีไซน์ และข้อจำกัดที่รู้อยู่แล้วแต่ยังไม่แก้

> **อัปเดต 2026-09-06:** เขียนใหม่ทั้งฉบับให้ตรงกับโค้ดปัจจุบัน — logic ทั้งหมดถูกแยกออกจาก `home-page.tsx` ไปอยู่ที่ [`src/lib/matching.ts`](../src/lib/matching.ts) แล้ว (เพื่อเขียน unit test ได้ ดู `src/lib/matching.test.ts`) เนื้อหาเก่าที่อ้างอิง localStorage/เลขบรรทัดใน `home-page.tsx` ถูกลบทิ้ง เพราะไม่ตรงกับของจริงอีกต่อไป

## Logic ปัจจุบัน — [`src/lib/matching.ts`](../src/lib/matching.ts)

1. **คัดกรอง pool ที่จับคู่ได้ก่อน** (`toEligiblePlayers` ใน `home-page.tsx`) — ตัดคนสถานะ `registered` (ลงชื่อล่วงหน้า ยังไม่เช็คอิน) ออก เหลือแค่ `checked_in`/`resting`/`playing`
2. **`rankCandidates`** — จัดลำดับ pool ตาม:
   1. `matches` (จำนวนแมตช์ที่เล่นจบไปแล้วในเซสชันนี้) น้อยไปมาก — หลักสำคัญที่สุด
   2. `queuedAt` (เวลาที่กลับเข้าคิวล่าสุด) เก่าไปใหม่ — ใครรอนานกว่าได้ก่อน ใช้ตัดสินเมื่อ `matches` เท่ากัน
   3. ก่อนเรียงจะ shuffle สุ่มลำดับทั้ง pool 1 รอบก่อนเสมอ (`shufflePlayers`, Fisher-Yates) กันกรณีเท่ากันเป๊ะได้ลำดับเดิมซ้ำทุกครั้ง
3. **`buildMatchesFromPlayers`** — ตัดคนจากหัวคิว (ตามลำดับข้อ 2) ลงคอร์ดทีละคอร์ด (2 คน/แมตช์สำหรับ singles, 4 คน สำหรับ doubles) ถ้าคนไม่พอสำหรับคอร์ดไหน **หยุดทันที** (ปล่อยคอร์ดนั้นว่างไว้ก่อน ไม่ทำแมตช์ไม่ครบคน)
4. **`assignTeams`** (เฉพาะ doubles) — กับ 4 คนที่ได้มา ลองแบ่งทีมได้ 3 แบบ (AB-CD, AC-BD, AD-BC) เช็ค `partnerHistory` (`timesPlayedTogether` ต่อคู่ สโคปต่อ session — ดู [database-design.md](./database-design.md)) เลือกแบบที่ผลรวมจำนวนครั้งที่เคยจับคู่กันมาน้อยที่สุด ถ้าเสมอกันหลายแบบสุ่มเลือก 1 ใน นั้น

เมื่อแมตช์จบ (`applyMatchFinishStats` ใน `src/lib/db/services/matchLifecycle.ts`) — ทุกคนในแมตช์ได้ `matches +1`, `queuedAt` รีเซ็ตเป็นเวลาปัจจุบัน, สถานะเปลี่ยนเป็น `resting`, และ `partnerHistory` ของแต่ละทีม (2 คน) ได้ `+1` — ค่าพวกนี้ป้อนกลับเข้ารอบถัดไปที่ข้อ 2-4 ทันที ทำให้เกิดการหมุนเวียนแบบไดนามิก ไม่ต้องมี timer/scheduler ใดๆ

**"ปิดคอร์ด"** ก็ผ่าน `applyMatchFinishStats` เหมือนกันถ้าแมตช์ที่ปิดมีสถานะ `playing` อยู่ (นับสถิติให้) แต่ถ้ายังเป็น `ready` (ยังไม่กดเริ่ม) จะไม่นับสถิติ — ดู `src/app/api/sessions/[id]/close-court/route.ts`

## ที่มาของดีไซน์นี้ (ทำไมไม่ใช่สุ่มเฉยๆ)

ปัญหาที่ user เจอจริงก่อนมีระบบนี้:

- **"1 คอร์ด 8 คน เล่นคู่ แทบไม่เปลี่ยนคู่เลย"** — สุ่มแบ่งครึ่งทั้ง pool โดยไม่ track ว่าใครเคยจับคู่กับใคร ทำให้จับคู่ซ้ำบ่อยเกินไปโดยบังเอิญ (มีแค่ 3 combination ต่อกลุ่ม 4 คน ยิ่งสังเกตซ้ำง่าย) → แก้ด้วยข้อ 4 (partner-history penalty)
- **"มาคอร์ดไม่พร้อมกัน อยากแฟร์กับคนมาก่อน"** — เดิมมีแค่ `matches` count ตัดสิน คนมาก่อน/มาใหม่ที่ยัง `matches=0` เท่ากันถูกปฏิบัติเหมือนกันหมด สุ่มล้วนว่าใครได้ลงก่อน → แก้ด้วยข้อ 2 (เพิ่ม `queuedAt` เป็น tie-breaker)

## ข้อจำกัดที่รู้อยู่แล้ว (ยืนยันแล้วว่ายังไม่ต้องแก้ตอนนี้ — คุยกันไว้ 2026-09-06)

### 1. ไม่มีระบบระดับฝีมือ (skill level)

จับคู่ตามคิวล้วนๆ ไม่สนใจฝีมือเลย อาจได้มือใหม่ปะทะมือเก๋าได้ — ผู้ใช้ยืนยันว่าไม่ต้องการฟีเจอร์นี้ตอนนี้ เพราะกลุ่มที่ใช้แอปเน้นตีออกกำลังกาย ไม่ใช่แข่งขันจริงจัง และการประเมินระดับฝีมือทำได้ยาก/เป็นภาระ

### 2. กันคู่หูซ้ำ (partner) ได้ แต่ไม่กันคู่แข่งซ้ำ (opponent) — และมีเคสที่กันคู่หูได้ไม่ครบทุกคนในห้อง

`partnerHistory` เช็คแค่ว่า 2 คนเคยเป็น**ทีมเดียวกัน**มากี่ครั้ง ไม่ได้เช็คว่าเคยเป็น**ฝ่ายตรงข้ามกัน**มาก่อนไหม และที่สำคัญกว่านั้น — **การเลือกว่า "ใครได้ลงคอร์ด" (ข้อ 3) ไม่มีการ mix กลุ่มเลย** ถ้าจำนวนผู้เล่นเป็นจำนวนเท่าของความจุคอร์ด (เช่น 8 คนพอดี 1 คอร์ดคู่ = ความจุ 4) ระบบจะล็อกเป็น 2 กลุ่มตายตัวสลับกันเล่นตลอดไป (คนกลุ่มที่เพิ่งเล่นจะมี `matches` เพิ่มขึ้น เลยแพ้คิวให้อีกกลุ่มเสมอ) **สองกลุ่มนี้ไม่มีวันได้อยู่คอร์ดเดียวกันเลย** ผลคือคนในกลุ่มเดียวกันจะจับคู่กันได้แค่ภายในกลุ่มตัวเอง (เช่น 4 คน หมุนคู่หูครบ 3 แบบแล้ววนซ้ำ) ไม่มีทางได้จับคู่กับอีกฝั่งเลยถ้าไม่มีคนเข้า-ออกเปลี่ยนสมดุล

ตัวอย่างที่ทดสอบจริง (8 คน P1-P8, doubles, 1 คอร์ด):

| รอบ | ใครลงคอร์ด | จับคู่กันยังไง |
|----|-----------|---------------|
| 1 | P1 P2 P3 P4 | P1+P2 vs P3+P4 |
| 2 | P5 P6 P7 P8 | P5+P6 vs P7+P8 |
| 3 | P1 P2 P3 P4 | P1+P3 vs P2+P4 |
| 4 | P5 P6 P7 P8 | P5+P7 vs P6+P8 |
| 5 | P1 P2 P3 P4 | P1+P4 vs P2+P3 (คู่สุดท้ายที่ยังไม่เคยลอง — บังคับ ไม่มีสุ่มแล้ว) |
| 6 | P5 P6 P7 P8 | P5+P8 vs P6+P7 (เหตุผลเดียวกัน) |

หลังรอบ 6 แต่ละกลุ่มลองคู่หูครบทั้ง 3 แบบพอดี 1 รอบใหญ่ แล้ววนสุ่มใหม่ทั้ง 3 แบบต่อไปเรื่อยๆ — แต่ **P1 จะไม่มีวันได้จับคู่กับ P5-P8 เลย** ไม่ว่าจะเล่นกี่รอบก็ตาม (ถ้าจำนวนคน/คอร์ดคงที่)

ผู้ใช้ยืนยันว่ายังไม่ต้องแก้ตอนนี้ (พอใจกับกันคู่หูซ้ำในระดับปัจจุบันแล้ว) — ถ้าต้องการแก้ในอนาคต ต้องปรับ logic ข้อ 3 (การเลือกว่าใครลงคอร์ด) ให้ผสม 2 กลุ่มเข้าด้วยกันเป็นระยะ ไม่ใช่แค่แก้ตอนจัดทีมภายในกลุ่มอย่างเดียว — วิธี workaround ชั่วคราวตอนนี้คือแอดมินกด "เปลี่ยนตัว" สลับคนข้ามกลุ่มเองระหว่างเล่น

## สิ่งที่เคยเป็นคำถามเปิด (ตอนนี้ตัดสินใจ/implement แล้ว)

- **`partnerHistory` scope ต่อ session หรือข้ามหลาย session** — ตัดสินใจแล้วว่า **สโคปต่อ session** (unique index `{ sessionId: 1, pairKey: 1 }` ดู [database-design.md](./database-design.md)) ไม่ carry ข้าม session
- **`queuedAt` reset เมื่อไหร่** — ตอนนี้ reset ทุกครั้งที่: เพิ่มผู้เล่นใหม่/เช็คอิน, แมตช์จบ (ปกติหรือถูกปิดคอร์ดตอนกำลังเล่น), ถูกเปลี่ยนตัวออก (substitute), หรือกด "รีเซ็ตสถิติ/แมตช์"
